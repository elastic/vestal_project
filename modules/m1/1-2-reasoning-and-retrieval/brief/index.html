Lab 1.2: Structured output and retrieval versus fine-tuning

Tina is Cortex Bank's AI compliance assistant. Her eligibility decisions pass schema validation, and some of them are still wrong. In this track you build a semantic validator and Tina's first retrieval pipeline, then decide how Cortex keeps her accurate.

The problem

Tina's decisions as Build 1 loads them. Every one is valid against its schema:

Loaded 7 dev decisions.
  dev-01: {'threshold': 10000, 'direction': 'at or above', 'reportable': True}
  dev-02: {'threshold': 6200, 'direction': 'at or above', 'reportable': True}
  dev-03: {'threshold': 10000, 'direction': 'at or above', 'reportable': False}
  dev-04: {'threshold': 10000, 'direction': 'at or above', 'reportable': True}
  dev-05: {'sar_deadline_days': 30, 'filing_required': True}
  dev-06: {'sar_deadline_days': 60, 'filing_required': True}
  dev-07: {'threshold': 10000, 'direction': 'above', 'reportable': True}

Three of them are wrong. Policy-003 sets the CTR threshold at $10,000, "at or above"; policy-011 sets the SAR deadline at 30 days. A validator that only checks the schema passes all seven, and Cortex files the wrong reports.

A reasoning trace, step by step

A reasoning trace
1. Retrieve policy-003 from the index
2. Parse the threshold: $10,000
3. Compare: $10,000 above $10,000 gives false
4. Set reportable: false
5. Return the decision JSON

Step 3 uses the wrong operator. At exactly $10,000, "above" gives false; "at or above" gives true. The schema says nothing about which operator is correct.

Schema checks shape; semantics check truth

JSON Schema can assertJSON Schema cannot assert
threshold is a numberthreshold matches the policy value
direction is a stringdirection uses the correct operator
reportable is a booleanreportable follows from the facts
all required fields presentagainst what source?

Schema validation checks form, not facts. Semantic validity requires comparing the decision's claims with the authoritative source.

The source is in Elasticsearch

cortex-policies holds 18 policy documents and the risk-scoring reference. Retrieve the governing rule with a semantic search on body_semantic, then compare the decision's threshold and direction with the retrieved text. That is semantic validation.

What retrieval changes

POST /cortex-policies/_update/policy-003-1
  -> refresh -> search
     the next query sees the new value
     (several seconds)

Update the document in Elasticsearch and the next retrieval sees the new value within seconds. The model's weights are untouched, and no retraining pipeline is needed.

What fine-tuning changes

collect data -> train -> evaluate -> deploy
     data pipeline + GPU time + eval
     (days or more)

Fine-tuning changes the model's weights. The data pipeline, training run and evaluation cycle take days. It suits behaviour that changes rarely, such as a fixed output format or defined terms, which retrieved text does not enforce.

Knowledge or behaviour

What changesWhat keeps up
Policy valuesRetrieval: seconds per update
Behaviour: format, defined termsFine-tuning

Cortex's values live in the corpus, in cortex-policies, so both rows keep retrieval for them. When the request itself carries every fact, there is nothing to retrieve, and fine-tuning alone can cover the behaviour. Your sandbox has one Cortex requirement, in /home/elastic/cadence-constraint.json, and that requirement decides the approach. Build 2 measures how fast one policy update reaches an answer; the Defend shows that number as evidence of how fast retrieval delivers a change. It does not change which row applies.

Building the pipeline

1. Semantic search: body_semantic, k=3
       |
2. Filter: effective_date <= now
       |
3. Inject the top-3 context into the prompt
       |
4. LLM answers with its source

Four steps: semantic search, date filter, context injection and the LLM call. You write the query in Build 2. The filter makes sure Tina sees only policy versions already in effect.

Decision rule

Take the first row that applies. The requirement seeded for your sandbox decides the row; your measured propagation latency is evidence, not the deciding factor.

  • Your new threshold in policy-003, and in Tina's answer to the CTR question
