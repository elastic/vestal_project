Lab 1.3: Build Tina, from completion to ReAct on Elasticsearch

Tina is Cortex Bank's AI compliance assistant, the system you build across this module. You choose her model tier, then build her in four stages, each one fixing the gap of the stage before: a bare model call, context from Elasticsearch, a search tool and a ReAct loop.

The problem

Q: What is Cortex Bank's internal threshold for
   filing a Suspicious Activity Report when the
   suspect is known, and is a $4,000 suspicious
   transfer by a known customer reportable?

Stage 1 recorded. Tina says:
... The internal threshold for filing a SAR when
the suspect is a known customer ... is **$5,000 or
more** ...

Therefore, a single **$4,000 suspicious transfer
by a known customer** is generally **not
reportable** under the mandatory FinCEN SAR
filing thresholds ...

Tina answered confidently from her training: $5,000 is the federal figure, and she consulted no source. Cortex's own threshold is $3,500, in policy-003, so this $4,000 transfer must be reported. Cortex would miss the filing. You see this yourself in Build 2, stage 1.

What a tier is

Four axes: cost per 1,000 requests, latency p50, capability on your task, and deployment constraints such as data residency or a limit on completion tokens per reply. A benchmark on the wrong axis picks the wrong tier.

Choose by constraint, not by benchmark

Cortex has three possible constraints: a data-residency rule, a cost ceiling per 1,000 requests, and a completion-token ceiling on completion tokens per reply. Your sandbox has one. Residency is a rule; the ceilings are decided by what you measure. Completion tokens include any reasoning a model does before it answers.

Stage 1: bare completion

User, then LLM, then answer. No source is consulted: the model generates from its training weights. Gap: no source.

Stage 2: context injection

Retrieve the top 3 chunks from cortex-policies and put them in the prompt. The model can cite sources. Gap: it can only read what you pre-loaded. It cannot ask for different documents mid-answer.

Stage 3: tool calling

Register search_policies(query) and the model calls it on demand. finish_reason: tool_calls triggers your dispatch, and the result returns as a role: tool message. Gap: one shot. A two-hop question needs two searches.

Stage 4: ReAct loop

Handle tool_calls, append each result, and continue until finish_reason: stop. The model reasons, searches again, and combines what several calls return. This is the target architecture.

The tool-call protocol

# assistant message
{"role": "assistant",
 "tool_calls": [{"id": "call_abc",
   "function": {"name": "search_policies",
     "arguments":
"{\"query\": \"SAR threshold known suspect\"}"
   }}]}

# your dispatch returns:
{"role": "tool", "tool_call_id": "call_abc",
 "content":
   "[{\"policy_id\": \"policy-003\", ...}]"}

Four messages: the assistant message with tool_calls, your code's dispatch, a tool message with the result, and the model's next turn. You implement the dispatch loop.

Your tool is a search

# tool schema
{"name": "search_policies",
 "description": "Search Cortex AML policies",
 "parameters": {"type": "object",
   "properties": {
     "query": {"type": "string"}},
   "required": ["query"]}}

# Elasticsearch query it runs
{"query": {"match": {
  "body_semantic":
    "SAR threshold known suspect"}}}

search_policies(query) runs a semantic search over cortex-policies. You write the schema, the dispatch and the loop that sends each result back to the model; the harness in /opt/ara/lib/tina/ supplies the client and ToolRegistry.

What done looks like

  • Recorded runs on each tier: 5
  • Best tier's mean field accuracy: at least 50%
  • Stages 1 to 4 run, with stage 2 grounded in the retrieved policy
  • Stage 3 calls search_policies with a relevant query
  • Stage 4 tool calls: at least 2, with 2 distinct queries, and both gold values in the answer
