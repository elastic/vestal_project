Lab 1.4: Harness and memory

Tina is Cortex Bank's AI compliance assistant. On turn three an analyst asks "Is that reportable?", and Tina has no idea what "that" is. Model calls have no memory. You give her one: implement the MemoryStore, then defend the harness posture that fits Cortex's constraints.

The problem

Turn one names the customer: Elias Vance, account 4492, $9,000 to $9,500 at ATMs daily for ten days. Here is what Tina says next, from the notebook's conversation cell with no memory store wired in:

Turn 2 recalled 0 memories:
Turn 2: I'm sorry, but I don't have any memory of a
previous conversation about a customer's withdrawal
pattern or wire transfers. Please provide more
context.
Turn 3 recalled 0 memories:
Turn 3: I need more information to answer your
question. What transaction are you referring
to?

Tina forgot the customer by turn two. Every LLM call starts fresh: the model sees only what the harness sends with that call, and nothing carried turn one forward. Cortex analysts cannot re-introduce the context every turn.

What a harness adds

The model is one box. A harness wraps it with memory (state that persists), tool dispatch (calling Elasticsearch), control flow (loops, branches) and tracing (audit). None of this lives in the model call itself.

Three memory scopes

Memory typeLives whereSurvives
Context windowThis API callOne call
Working memoryThis conversationThis session
Persistent memoryExternal storeAcross sessions

"That" in turn three needs working memory: it must survive the conversation, not necessarily across sessions. Scope is set by when the store is cleared, not where it lives. The right scope avoids storing too much (everything persistent) and too little (the context window only).

Your memory store is an index

# cortex-tina-memory mapping
{
  "mappings": {
    "properties": {
      "turn":     {"type": "integer"},
      "entities": {"type": "text"},
      "summary":  {"type": "text"}
    }
  }
}

# remember: index one doc per turn
# recall:   search on entities + summary

cortex-tina-memory is a small Elasticsearch index. Remember indexes a document per turn. Recall searches it by entity or topic. It stays on the same stack as cortex-policies.

Three harness postures

PostureControl flowCortex use
SequentialOrdered stepsCompliance audit trail
GraphBranch on resultsRisk-tiered escalation
Event-drivenReact to triggersWire alert on arrival

Sequential runs fixed steps in order: auditable and predictable. Graph branches on what each step returns: flexible, and harder to trace. Event-driven reacts to external signals: responsive, and it needs durable queues.

Decision rule

Take the first row that applies. Your sandbox has one constraint, and the Defend grades your posture choice against it.

ConstraintCorrect postureWhy
Strict step order with audit trailSequentialFixed sequence, each step logged
Branch on tool resultsGraphConditional paths require branch nodes
React to incoming eventsEvent-drivenExternal trigger drives execution
