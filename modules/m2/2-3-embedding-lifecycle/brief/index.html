Lab 2.3: Embedding lifecycle

A new embedding model is available. Before it ships, you must benchmark it, cut over without downtime, and raise recall for the queries it still gets wrong.

The problem

Embedding models improve — but deploying a new one risks regression. Cortex Bank's compliance corpus must stay searchable during the swap.

The alias cortex-corpus-live is the indirection layer. You will move it atomically once the candidate is ready.

What you will do

  • Build 1 — Benchmark: Run held-out queries against both models. Measure nDCG@5 gain and p95 latency.
  • Build 2 — Cut over: Swap cortex-corpus-live to the candidate index in one atomic _aliases call.
  • Build 3 — Raise recall: Rewrite the three lowest-scoring queries using query-side rewriting to close remaining recall gaps.
  • Defend: Justify the deployment decision given the gain, noise band, and latency budget.

Deployment decision framework

ConditionDecision
Gain > noise band AND p95 within budgetDeploy
Gain ≤ noise bandHold — gain is noise
p95 exceeds budgetHold — too slow
Both conditions failHold — insufficient and slow

Key concepts

  • nDCG@5 — ranking quality metric; higher is better
  • Noise band (0.03) — gains below this are measurement noise
  • Atomic alias swap — remove + add in one request; zero downtime
  • Query-side rewriting — fix recall without touching the index
