Lab 4.1

Lab 4.1: Agent Builder fundamentals and core tools

Tina now lives in Elastic Agent Builder, over Cortex's wire, cash, ATM and brokerage data. She has one tool, a policy search. You give her the two tools her analysts need first, and prove she reaches for each one when she should.

Tip: Select Hide Instructions in the top bar to give the Brief full width.

The problem

The answer is right: those are the six deposits. Now try to sign it off. Tina had no tool for the question, so she wrote her own: fourteen raw Elasticsearch requests through the platform's internal API tool, with filters, band and window she chose on the fly. Nobody reviewed that query, the next run may write a different one, and the record shows "execute_api" fourteen times rather than one named check with an account and a window. She also volunteered a wire-transfer finding nobody asked for.

A compliance desk needs the opposite: one reviewed query, called by name, with the account and the window as typed values you can read back. That is a tool, and Tina picks it by what its description says.

Fixed chain or agent loop

agent loop: the model picks each step

  question
    |
    v
  plan     which tool, with what values?
    |
    v
  act      call it
    |
    v
  observe  read the result
    |
    +--> enough?  no: plan again
    |             yes: answer
    v
  answer

fixed chain: the author picks each step

  inputs -> enrich -> rate -> write
            the same order, every run

An agent decides its next step after it reads the last result, so the same question can take a different path. A workflow runs the steps its definition lists, in that order, every time.

Neither is better. A lookup an analyst phrases a hundred ways wants the loop; filing a case the same way every time wants the chain. A chain can still hold one step that is itself an agent.

Tool types

TypeRunsFits
ES|QLOne query you wrote, with typed parametersFilters and aggregates over structured fields
Index searchRelevance search over one index, query phrased by the modelFree text answered by passages
Workflow (Technical Preview)A whole workflow, as one callSeveral steps in order, often with a write
MCPA tool served by another system over MCPCapabilities that live outside Kibana

The query in an ES|QL tool is yours: the model fills only the parameters. The query in an index search tool is the model's: it phrases it from the question. That difference decides which one a request needs.

Parameters are a contract

FROM cortex-wire-transfers
| WHERE account_id == ?account_id
    AND ...
    AND DATE_DIFF("day", @timestamp, NOW())
        < ?lookback_days

params
  account_id     string
    "The Cortex account number, exactly as
     the analyst wrote it, for example 1981."
  lookback_days  integer
    "How many days back from today to look,
     taken from the question."

tool call Tina makes
  {"account_id": "1981", "lookback_days": 7}

Each ?name in the query is a value the model supplies. The type and the description are all it knows about that value: a description that only repeats the name gets you whatever the model guesses.

Parameters fill values, never query syntax. A window is a comparison on a parameter, not a parameter glued to a unit.

The description is the routing signal

"Did account 476 deposit just under
 10,000 in the last 7 days?"

description A: "ES|QL tool"
  route  cortex.policy_search
  wrong tool: nothing said this one fits

description B: "Finds structuring on one account:
  cash deposits just under the 10,000
  threshold in the last N days. Use it when
  an analyst names an account ... Do not
  use it for policy questions."
  route  cortex.structuring_deposits
         (account_id=476, lookback_days=7)
  right tool, right values

Tina reads every tool's description on every turn. Say what the tool finds, which questions it answers, and which questions belong to another tool. The last part is what keeps a policy question about structuring out of your detector.

The check grades routes on held-out questions, not your words, so test with the dev set until the routes are right.

Workflow tools: many steps, one call

Tina: cortex.open_case(account_id=476,
                       pattern=structuring,
                       findings=...)
  |
  v
cortex-open-case (Technical Preview tool)
  1 enrich   elasticsearch.search
             cortex-ref-accounts
  2 rate     ai.classify -> critical | high
                              medium | low
  3 write    elasticsearch.index
             cortex-fraud-cases
  |
  v
tool result: execution id, status

A Workflow tool hands Tina a whole procedure as one call. She decides when to open a case and with what values; the workflow decides how, in an order she cannot change. Rate before you write, or the record is written without its rating.

An AI step inside a workflow uses a model too: ai.classify picks one of your categories, and ai.agent runs an agent and can return a schema. Workflows run as the caller, so Tina's key decides what the write may touch.

The record of what Tina did

converse response
  steps
    tool_call  cortex.structuring_deposits
               params  {"account_id": "476",
                        "lookback_days": 7}
               results esql_results, 5 rows
    tool_call  write_todos   internal
  response.message  "Account 476 made five ..."

route the check grades
  cortex.structuring_deposits(476, 7)

Every conversation records each tool call with its parameters and results. The check reads that record: which custom tools Tina called, in what order, with what literal values. It never grades her prose, and it ignores the platform's own internal tools.

A model's route varies a little from run to run, so the check passes at a count of questions, not all of them. The count comes from calibration runs of a reference solution.

Decision rule

Take the first row that applies.

The requestTool typeWhy
Several steps in a fixed order, one of them writes a recordWorkflow toolOrdered steps with a side effect
Typed values (an account, a number of days, an amount) into one query over fieldsES|QL toolTyped parameters, fixed query
Free text answered by the passages that match it bestIndex search toolRanked text

One type, one reason. The type that could do the job badly is still the wrong type.

What done looks like

  • 5 of 6 held-out questions routed with the right tool and the literal account and days
  • 3 of 3 held-out case requests routed, run to completion, and written as one case each

Also checked:

  • Your detection tool, run for account 1981 over 7 days, returns every cash deposit just under the threshold in that window and nothing at or over 10,000; for account 1234 it returns nothing
  • Descriptions: at least 20 words for the tool, 8 for each parameter
  • The workflow rates before it writes, and every case carries its own execution id
