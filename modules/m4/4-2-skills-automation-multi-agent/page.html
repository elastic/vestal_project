Lab 4.2: Skills, automation, and multi-agent composition

Tina can now detect structuring and open a case when an analyst asks. The desk wants three more things: the morning sweep to run without anyone asking, triage done the same way every time with clear limits, and brokerage questions answered by a specialist rather than improvised.

Tip: Select Hide Instructions in the top bar to give the Brief full width.

The problem

Tina has no brokerage tool, so she invented a definition of wash trading on the spot (one account buying and selling the same symbol) and wrote her own queries for it. The planted ring is four accounts trading QNTM with each other. She found two of them, missed two, and named five accounts whose one buy and one sell are ordinary trading. Her own answer says the search was cut off at 200 accounts.

Nobody can sign off a securities finding whose route shows no securities check. Cortex has those checks; they belong to a specialist who knows when to use them.

Two more gaps sit behind it. The sweep for structuring runs only when someone remembers to ask. And triage is whatever Tina decides that turn: nothing written says she must detect before she opens a case, or that a request to close an account is not hers to act on.

Standalone automation or a tool an agent calls

standalone workflow
  trigger (clock, alert) -> steps -> records
  no conversation, no agent deciding to start it

workflow tool (Lab 4.1)
  Tina, mid-conversation -> tool call -> steps -> result
  the agent decides when, the steps decide how

The same workflow engine runs both. What differs is what starts the run. If someone asks Tina and she picks the moment, the workflow is a tool on her. If nobody asks, a trigger starts it, and no agent is involved in deciding to run it.

A standalone workflow can still use AI inside it: a step that rates or classifies is part of the procedure, not an agent choosing what to do next.

A workflow can carry more than one trigger. Keep manual beside scheduled so you can run it on demand while you build it.

Iteration and branching

detect     elasticsearch.esql.query
           -> values: [["1981", 6, 55971.15],
                       ["476",  5, 46809.7]]
each       foreach steps.detect.output.values
  rate     ai.classify   critical|high|medium|low
  route    if rating : high or critical
             steps  write cortex-fraud-cases
             else   write cortex-audit

A foreach runs its inner steps once per item, and foreach.item is the current item. An ES|QL row is a list in column order, so foreach.item[0] is whichever column the query keeps first. Keep the account first.

An if takes a KQL condition on earlier steps' output and runs steps or else. Putting the case write inside the branch is what makes the rating decide it: a write outside the if runs whatever the rating says.

Every record carries the run's execution_id, so you can find exactly what one run wrote.

Skills: tools plus a playbook

skill cortex-fraud-triage
  description  when to load it
  tools        cortex.structuring_deposits
               cortex.open_case
  content      1. Detect with cortex.structuring_deposits
               2. No rows: stop, no case
               3. Rows: cortex.open_case for that account
               4. Report what you found

A skill is a procedure packaged with the tools it uses. Tina loads it when a request matches its description, and the playbook tells her the order. The tools come with it, so an agent can use a skill's tools without holding them itself.

A playbook written as numbered steps, each naming its tool, is easier for Tina to follow and for a reviewer to check than a paragraph.

Instructions: grounding, engagement, escalation

RuleSaysNames
GroundingPolicy answers come from the policy documents, never from memorycortex.policy_search
EngagementWhat Tina does on her own: open a case when a detection returns the accountcortex.open_case
EscalationOut-of-scope or irreversible requests go to a person; she does not act on themcortex.escalate

The skill says how to triage. The instructions say what Tina may do at all, for every request. Name the tool in each rule: it is how she connects a kind of request to the action that handles it.

Escalation is an action, not a refusal: cortex.escalate records the request for a person, so it is not lost.

A general rule often covers what the model does anyway. A rule earns its place when it says what Tina cannot guess. In our runs, with a general escalation rule, Tina ran triage on an account held by a Cortex employee and opened a case on it, because nothing told her that Cortex sends insider cases to the Board Risk Committee instead. Those are the Cortex rules in the decision rule below.

Allocation: coordinator and specialists

tina-compliance  (coordinator)
  tools   policy_search, structuring_deposits,
          open_case, escalate
  sub-agents
    cortex-securities-irregularities
      tools  securities_layering, wash_trading,
             unexplained_wealth, open_case

A specialist owns the tools only it uses, with instructions for that domain. The coordinator keeps the questions she handles and hands the rest on. A tool both need, such as opening a case, sits on both.

Leave a specialist's tool on the coordinator and she can answer the question herself, skipping the specialist you built for it. The check fails that allocation before it asks Tina anything.

Two delegation styles

A third route, agent-to-agent (A2A), runs the other way: Agent Builder serves each agent over A2A, so an agent in another system can hand it a task. This lab does not build it.

Tina picks a sub-agent by its description, the way she picks a tool. Say which questions it handles in words an analyst would use.

A delegated question takes about a minute: Tina plans, the specialist plans and runs its tools, and Tina reads its answer back.

What least privilege cannot do here

remove brokerage tools from Tina
  she still holds execute_api   internal, cannot be removed
  she still runs as the caller's key
  the specialist runs as the same key

Tool lists allocate work; they do not enforce access. Internal tools stay on every agent, and every agent runs with the key of whoever is asking. A key with no read on the trades index makes the specialist's tool fail too.

What keeps securities questions with the specialist is Tina's instructions and the specialist's description. What keeps the data safe is the key.

What done looks like

  • The sweep, run by the check: one iteration per account to review, and one record per account in the index its rating calls for
  • All 4 held-out conversations on the expected route: detect before a case, escalate what Tina must not do, policy from the policy search, each under the Cortex rules
  • At least 7 of 8 (aim for 8) held-out questions allocated right: securities to the specialist with the right brokerage tool, everything else kept by Tina, under the Cortex rules

Also checked:

  • The sweep is enabled, scheduled, has a foreach with an AI step, and writes cases only inside an if
  • The skill holds and names both tools and has at least 3 numbered steps; Tina's instructions name the grounding, engagement and escalation tools
  • The specialist's description has at least 8 words; Tina holds no brokerage tool
