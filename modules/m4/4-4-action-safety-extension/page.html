Lab 4.4: Action safety and extension

Tina can now file a suspicious activity report (SAR) with the regulator, and the desk wants her to cite the statute behind each pattern from a page on the open internet. Before either goes further, you need to know which of her actions can be taken back, and what stands between a request and the ones that cannot.

Tip: Select Hide Instructions in the top bar to give the Brief full width.

The problem

The same offhand sentence went to two agents with the same tool. Tina escalated, because her Lab 4.2 escalation rule told her to. The desk agent filed, and in this run it did not even look at the account first. The filing has status transmitted, and under Cortex's rule a transmitted SAR cannot be withdrawn. Nothing between the sentence and the filing asked anyone.

The difference was in each agent's instructions, not in the tool. Any agent given cortex.file_sar can file, and whether it does depends on the model following its instructions. That makes an instruction a request, not a control. The control has to sit on the action itself.

Reaching outside Cortex

Tina --calls--> cortex.read_page            Workflow tool
                  -> cortex-read-page        workflow: one http GET
                       connector-id: cortex-jina-reader
                         url  https://r.jina.ai       (the service)
                         secrets  none here           (where a key would live)
                  -> https://r.jina.ai/<page URL>  ->  page text

Every tool so far stayed inside Cortex. To cite a statute, Tina has to read a page on the open internet. The Jina Reader takes any page URL and returns its text, which an agent can read; it is free without a key at 20 requests a minute.

Three objects give her that reach. A connector holds the outside service's address and, when the service needs one, its credential, so the secret lives in one place and no workflow carries it. A workflow step names the connector with connector-id and gives only a path. A Workflow tool (Preview) turns the workflow into something Tina can call, and her tool list decides whether she can.

A bad credential: seen or hidden

PathA bad key shows up as
A workflow http step through a connectorThe step and the run fail: ConnectorExecutionError [401] Invalid API key
An agent calling a connector directly (platform.core.execute_connector_sub_action)The trace span says Ok; only the tool's result says ok: false, code 401

The second row is a measured platform fact: measured on Serverless in 2026, in this certification's design research, with an agent calling the Jina connector's browse with an invalid key. The span's status.code was Ok, with no error type; the step result held ok: false, code: 401. The call to the connector succeeded, so the trace recorded success, though the service refused the key. A dashboard of span statuses would show nothing wrong.

So judge a call to the outside by its result, never by the trace's status. A workflow makes that easier, because a refused key fails the run where anyone reading it can see. Build 1's check reads the run.

Plugins and hand-written skills

hand-written skill   cortex-fraud-triage
  lives in           this space; edited in place
  names              this space's tools: cortex.structuring_deposits, cortex.open_case

plugin               cortex-compliance
  installs from      a source URL at a fixed ref   (/tree/<ref>/...)
  skills             cortex-compliance-regulatory-citation   read-only
                     cortex-compliance-case-escalation-memo  read-only

A plugin (Preview) is a package of skills in the Claude agent plugin format, installed from a URL. The ref in the URL fixes the version: every project that installs from it gets the same skills, and nobody edits them in place. Installing puts the plugin in the space; an agent uses it only when its id is in the agent's plugin_ids.

A hand-written skill is the opposite trade. It is edited where it lives and can name the exact tools of its space, which is why it suits a playbook built around one desk's tools. A plugin carries skills and tool definitions, not the backends behind them: tools it names must already exist where it lands.

Three action classes

tool type          what to read                      class
ES|QL, search      the query                         read-only
Workflow           each step: what it writes, where
  writes cortex-fraud-cases, cortex-audit, flags     side-effecting
  writes cortex-sar-filings (transmitted)            irreversible
  http POST to a host outside Cortex                 irreversible

The class comes from the tool's definition, not its name or description. For a Workflow tool, open the workflow and read its steps, including the ones inside if and foreach: the index each write targets, and the host of each http step.

Side-effecting means the effect stays inside Cortex and can be corrected or removed: a case can be closed, a flag cleared, a hold lifted. Irreversible means nobody at Cortex can take it back: a SAR once transmitted, or data once it has left for another organization.

Controls per class

ClassRequired controlWhy
read-onlynoneNothing changes
side-effectingaudit entryA mistake can be found and reversed
irreversibleapproval gate plus audit entryA mistake cannot be reversed, so a person decides first, and the decision is recorded

The gate goes in the workflow, where the action happens, so it holds whoever calls it: Tina, a scheduled run, or a coding agent over MCP. Agent Builder also lets a Workflow tool ask the chat user to confirm before it runs; that protects one caller, in one interface, and is not built in this lab.

Approval: pause, resume, decline

run  -> waitForApproval   status waiting_for_input
           resume {"input": {"approved": false}}
        -> step completes, output.response.approved = false
        -> if steps.approve.output.response.approved : true
             steps:  file_sar        skipped
        -> audit                     runs
run status: completed

A waitForApproval step (Preview) pauses the run until someone answers it. Resuming with approved: false does not fail the step or cancel the run: the step completes with that answer and the run carries on. Only an if that reads the answer keeps the filing from running.

So the audit entry belongs on both branches. A decline is a decision too, and the record of who declined what is part of the control.

Decision rule

Take the first row that applies.

Tool definition showsClassRequired control
A workflow that writes to cortex-sar-filings (transmitted, cannot be withdrawn), or sends data outside Cortex (a POST or a body to a non-Cortex host)irreversibleapproval gate plus audit entry
A workflow that writes only Cortex records that can be corrected or removed (cases, escalations, audit, flags, holds)side-effectingaudit entry
An ES|QL or index search tool; a workflow whose only outside call is a GET of a web page, sending no Cortex dataread-onlynone

Read the definition, not the name: what is written, where, and can it be undone.

What done looks like

  • Asked which US Code section governs the pattern on account 1981, Tina reads the pinned page through cortex.read_page, and the read completes, on at least 2 of 3 runs (aim for 3)
  • The cortex-compliance plugin installed from the pinned URL and attached to Tina
  • Every action Tina can take classified, with the reason and the control, matching her definitions
  • cortex-file-sar gated: a declined run completes with 0 filings and 1 audit entry; an approved run files 1 and audits 1
