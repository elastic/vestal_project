Lab 5.1: Access control

Tina is about to serve more desks at Cortex Bank and Trust. A first-line analyst may see low- and medium-risk cases but never a customer's identifiers; an investigator on the financial-crimes desk sees every field of the case types the desk owns. Before the rollout, you need to know what each caller's key lets Tina retrieve, and to make the policy hold where it counts.

Tip: Select Hide Instructions in the top bar to give the Brief full width.

The problem

Tina kept the house rule: her answer named no one. Her tool did not. The tool result held every structuring case, the high-risk ones a first-line analyst may not see, each with the subject's name and TIN. That result sits in the conversation, where the next question, the next model call or anyone reading the conversation can reach it.

The house rule shaped what Tina said. It did not decide what she retrieved, and nothing in her instructions can. What a tool returns is decided by the privileges of the key that called it.

Two layers of access

caller's key ──> may it use Tina?          agent access: public, shared with
                                           named users, or private
             ──> what may Tina retrieve?   the key's privileges, on every
                                           index her tools read

The first layer decides who reaches Tina at all. Tina is public, so any key whose owner may use Agent Builder reaches her. Sharing names individual users, never roles, and a private agent is invisible to a role key even when the key's owner made the agent.

The second layer decides what she can bring back for that caller. Tina has no privileges of her own: every tool she calls runs with the caller's key. This lab is about the second layer.

API keys

POST /_security/api_key
  { "name": "cortex-auditor-key",
    "role_descriptors": { "cortex-auditor": { indices, applications, ... } } }

effective access  =  role_descriptors  ∩  limited_by (the creator's privileges)

A key's role_descriptors say what it may do. Elasticsearch also records limited_by, the privileges of the user who created it, and the key never exceeds them: descriptors broader than the creator's role give nothing extra. Two cases follow from the same rule. A key created with empty role descriptors carries a snapshot of its creator's privileges. A key created by another API key, rather than by a user, can only be created with no privileges, and has no authority to call Elasticsearch: it reaches nothing.

A key does not take a role by name. To give a key a role's privileges, put the role's body in its descriptors.

Tools run as the caller

Tool typeRuns asUnder a restricted key

Workflow (Preview)the caller, step by stepKibana checks workflow_execute before any step runs; each step then reads and writes with the key's index privileges
HTTP APIthe callerthe request carries the caller's privileges

This holds whether the tool is called by Tina in a chat or directly through POST kbn:/api/agent_builder/tools/_execute, which is how the helpers and the checks in this lab probe a key. A call ends in one of five ways: rows, no_rows, error_hidden_field (an ES|QL query named a field the key cannot see), error_not_authorized (refused before the tool could do anything), or error_at_write (a workflow started and failed when it wrote).

Document and field security

{ "names": ["cortex-cases"],
  "privileges": ["read", "view_index_metadata"],
  "query": {"terms": {"risk_tier": ["low", "medium"]}},            document security
  "field_security": {"grant": ["*"], "except": ["subject_tin"]} }   field security

Document security (DLS) is a query on an index block: the key sees only the documents it matches, in every search, ES|QL query and tool. Field security (FLS) removes fields from every document the key sees. Both bind only the indices the block names; an index the role does not restrict stays open, and an index it holds no privilege on is refused outright.

FLS hides fields, not text. A case's title and body name the customer and often the account, and those stay readable to a first-line analyst; the policy here covers the identifier fields. Removing an identifier from free text is a different control, redaction at ingest, which Lab 5.2 builds.

A tool that names a hidden field

cortex.case_lookup under a key whose field security hides subject_tin:
  verification_exception ... line 3:73: Unknown column [subject_tin],
  did you mean [subject_name]?

An ES|QL query that names a field the key cannot see does not skip it: the whole query fails, and the caller gets nothing. That includes KEEP with a pattern that matches only hidden fields. So a tool written for the widest role can stop working for a narrower one. A query that names no restricted field returns what each caller's role shows: identifiers for a caller who may see them, none for one who may not.

The audit trail

workflow run under cortex-analyst-l1-key    executedBy: admin
workflow run under the admin user           executedBy: admin
conversation started under any key          author: admin, access: private to admin

A workflow run records the user who owns the key, never the key. Every key in this sandbox is created by the same project admin user, so the run record is the same whichever key called Tina. Conversations belong to that user too, not to the key.

Measured while this lab was built: a first-line key posted a new question into a conversation an investigator's key had started. Tina made no new tool call: the TIN came from the earlier round's tool results, already in her context. With the house rule she refused to repeat it, every time. No tool ran, so field security had nothing to filter; only her instruction stood in the way.

Decision rule

A restricted document or field reached a restricted role. Take the first row that applies.
