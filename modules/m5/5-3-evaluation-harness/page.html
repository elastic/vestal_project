Lab 5.3: Build the evaluation harness

Until now you changed Tina and looked at what happened. A change you cannot measure is a guess, and a measurement you cannot trust is worse, because it looks like an answer. In this lab you build the measurement: a test set curated to match what analysts really ask, a retrieval baseline, a routing baseline, and a model judge you prompt, tune and test, then use to name a defect planted in this sandbox's answers.

The problem

Both numbers look like good news and both are wrong to rely on. The first set holds only questions Tina answers well, so its 100 percent is a property of the set, not of Tina. Routing accuracy also reads only which tools she called, so it cannot see an answer that quotes the wrong passage, or one that ignores the question. The second is a judge written the way most first drafts are: one prompt, a score, a plausible reason. On records it was not tuned on it missed a defect in every run.

While this lab was built, Tina's route was right on about 95 percent of the lab's question pool, and on 98 percent of a second set written to be harder, in every category. A set that only checks routes cannot tell you where an agent is weak, because on questions like these her routes are rarely the weak part, and the weakness this lab plants is in the answers. An evaluation harness exists to make that visible before the agent ships, and to stay trustworthy afterwards.

A test set is a list of questions, each with what a right answer looks like. A run sends each one to the agent in a fresh conversation. Metrics turn each answer or route into numbers, records store them so a later run can be compared, and a comparison reads two labelled runs. In a new build you write the harness first, with the success criteria, and then the agent. This one is single-turn: each question is one message. Multi-turn evaluation is its own category and needs its own design.

The golden set

Cortex keeps a log of what analysts ask Tina. A test set drawn from the questions that are easy to write drifts toward the happy path. Curate it to the log instead. Label each question with a category, and make sure every category that is a tenth or more of the log has at least three questions in your set:

CategoryWhat it tests
straightforwardOne desk, every parameter stated
ambiguousA parameter is missing, or the answer spans several documents
time_window_edgeA window longer than the data, or a calendar period
cross_domainTwo desks in one question
adversarialTries to skip a rule, claims authority, or asks for an identifier
out_of_scopeA plain request that belongs to cortex.escalate

The check compares your labels with the log's own and expects most of them to agree: two people labelling the same question disagree sometimes, so treat a label as a judgement, and a set with no non-straightforward category as a set that cannot find anything.

Retrieval is measured by _rank_eval

For policy questions the thing to grade is what the search returns. Elasticsearch's _rank_eval API runs rated requests against an index and scores them. Three metrics, each at k = 5:

MetricReads
Precision at 5the share of the top 5 results that are relevant
Recall at 5the share of all relevant passages that reached the top 5
nDCG at 5whether the relevant passages are ranked near the top (normalised discounted cumulative gain)

Rate every result you want counted: a passage you did not rate is not treated as irrelevant unless you set ignore_unlabeled to false, which this lab does. The check re-runs _rank_eval itself and compares its numbers with what you stored, so a figure you edited does not agree with it.

The grading ladder

1  code checks       a route matched, a field present, a number in range        cheap, exact, narrow
2  a model judge      interpretation: is the answer supported, on topic          cheap, broad, noisy
3  human review       high-stakes or new behaviour; the labels a judge is calibrated against

Use the lowest rung that can answer the question. Route matching is a code check. Whether an answer follows from its passages needs interpretation, so it needs a judge, and a judge needs humans to say what its scores should have been.

Model-judged quality: three metrics

The vocabulary below is from the RAGAS evaluation family. Each metric reads a different slice of the record, which is why one can flag a defect another cannot see:

MetricReadsIgnores
Faithfulnessthe passages and the answer: is every claim in the answer supportedthe question
Answer relevancethe question and the answer: does the answer address what was askedthe passages
Context precisionthe question and the passages: are the passages the ones the question neededthe answer

Here the judge is an ES|QL query. COMPLETION sends a prompt to a model endpoint from inside the query, so a record (question, passages, answer) goes in and a score comes out, one COMPLETION per metric. Use a model different from the one being judged: a model rates answers in its own style higher.

Three failure modes, and which metric flags each

FailureWhat the record looks likeThe metric that drops
unfaithful_to_contextthe answer states something the passages do not supportfaithfulness
faithful_but_off_questionthe answer follows its passages and does not address the questionanswer relevance
wrong_context_retrievedthe answer is faithful and relevant to passages that do not fit the questioncontext precision

Each defect makes one metric drop and leaves the other two high, so a judge that scores only one metric misses the other two kinds. That is why this lab asks for three.

Writing a judge prompt

Write each metric as a definition: what it reads, and what it ignores. Give a small fixed scale and define every value, for example 0, 0.5 and 1, with what each means. Ask for the score first and one sentence of reason after it, because the harness reads the first number and a reason helps you debug a wrong score. A scale of 1 to 10 invites a model to pick a number it cannot justify.

The harness reads the first number it finds in each reply and snaps it to the scale. A reply that begins with prose can put the wrong number first.

Tune on known records, trust on held-out ones

Your sandbox holds labelled records: each says which defect it carries, or none. Tune your prompts until each defect's own metric drops where the other two hold and the clean records score 1. A judge tuned on a handful of records can fit them, so the check scores eight records you have not seen. A defect record's own metric must sit well below its others; a control must score 1 on all three. The check says how many it missed and which kind of defect, and never shows the record. Hold-out is how you find out whether a prompt learned the metric or learned the examples.

Judge variance

The same query can score the same record differently on two runs. A single run is a sample. The gate runs the eight records five times and asks each one to pass in at least four of the five. A judge that passes three times out of five is not a gate, and two single runs that differ prove nothing by themselves. Cost scales the same way: five runs of eight records is forty judge calls per gate, and the harness records what each costs.

Run records, and where cost comes from

Every run stores one document per question in cortex-eval-runs: route, tool-call count, input, cached input and output tokens, latency, the conversation id, and the judge scores. The token counts come from the converse response, model_usage, which reports them for each question. Traces are a separate, later subject: a harness number is never read from a trace, so it does not depend on tracing being on.

A metric that stays high on a defect would not have flagged it: Defend asks you to name one, with the reason it reads the wrong slice of the record.

What done looks like

  • Build 1: a test set of 18 to 30 questions from your log, at least 6 about policy and 10 for the agent, at least 3 in every category that is a tenth of the log or more; most of your labels match the log's; a retrieval baseline that agrees with the check's own _rank_eval within 0.005; a routing baseline recorded.
  • Build 2: a three-metric judge query that meets the contract, scores the planted record's own metric at least 0.5 below the other two and the controls at 1, passes the eight held-out records in at least four of five runs, and a diagnosis that names this sandbox's defect.
  • Defend: where your set departs from the log, which metric would not have flagged the defect, and the risk a described harness carries.
