Lab 6.1: Diagnose agent behavior from traces

An analyst reports that one of Tina's answers was incomplete. Three weeks of her rounds are in the trace stream. Find the failing step, the costly step, the tool whose query cannot match, and the capability she lacks.

Tip: Select Hide Instructions in the top bar to give the Brief full width.

The problem

The ticket says one of Tina's answers was incomplete. The dashboard shows an overall error rate that looks fine and a slow round or two. Neither tells you which step failed or which step made the round expensive.

Found nothing is not the same as could not have found anything. A tool that returns empty on every call, with matches in the data, is a different failure from one that returns empty because there was nothing to find.

One trace per round

Every conversation round with Tina is one trace. Its spans nest: the round, the agent execution, model calls (every token counted), tool calls (arguments and result, no tokens of their own) and workflow runs. A span carries the conversation id in attributes.gen_ai.conversation.id, so a ticket's conversation id finds its trace. The round's trace_id works too, but is undocumented.

Spans, and where cost lands

A tool span has no token count. A large tool result is paid for by the next model call, which reads it as input. So the costly step is a model call, and the question is which earlier step put the tokens there: a whole page returned by cortex.read_page, message bodies from cortex.case_correspondence, or the third of three near-identical searches.

Two traps in the trace stream

A tool span is marked Error only when the parameters fail validation. An error the tool returns as its result sits under Ok, so read the result. Content fields are keyword with ignore_above: 1024, so a longer value reads as null in ES|QL: read it from _source. There is no row-count field either: an empty result is read from the result content.

Reading a tool definition

A custom ES|QL tool's span carries its parameters, never its query. Read the query in the tool's definition, run it by hand with the span's parameters, and run the underlying data directly to see whether the thing it looks for exists. A tool that returns nothing on every call while the data holds matches cannot match: its query is wrong, not the data.

Gaps and escalations

An escalation is right or wrong by Cortex policy, not by count. Out-of-scope questions are meant to escalate. The ones to chase are a class Tina escalates because no tool answers it, or because a tool exists and is not attached. Building the missing tool and attaching it are separate steps: attaching changes every route, so it needs a measurement.

Trace content is sensitive data

The trace settings decide what a span holds: names, ids, prompts, tool details, model responses, and (off here) the system prompt and user data. Without real names every custom tool, agent and workflow reads as custom. Anyone who can read the stream reads every trace, so a trace with content capture holds what Tina saw, including PII. Retention follows the data stream's lifecycle.

What done looks like

  • Build 1: the five fields on the ticket's round.
  • Build 2: the defective clause named, and the tool's query fixed with its id, parameters and description unchanged.
  • Build 3: the missing capability named, and its tool built and not attached.
  • Defend: which case each summary is, and which earlier step put the tokens in your costly call.
