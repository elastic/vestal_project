Lab 6.2: Close the self-improvement loop

Cortex wants a weekly review of Tina's traces that proposes improvements. A model reads the week and writes proposals. Nothing reaches Tina until a gate that measures the change says it passes.

Tip: Select Hide Instructions in the top bar to give the Brief full width.

The problem

Both proposals cite real conversations and give a plausible reason. One lifts its target category and drops another, or raises cost past anything Cortex would accept. Reading them does not tell you which. Measuring does.

The evaluator pattern

A second agent, the evaluator, reads Tina's traces and run records and writes structured proposals. It never applies them. If it did, it would be grading the system it changes, and the traces it reads hold text outsiders wrote: a correspondence body or an analyst prompt can reach it, as M5's payloads reached Tina.

The proposal

A proposal has: kind (improvement); proposal_type (instruction_change, tool_description_change, tool_query_change, attach_tool, detach_tool); target (an agent id or a tool id); change (the tool_id for attach or detach, otherwise field and text); evidence (at least one item: a conversation_id, a trace_id and a short observation); expected_effect (metric and category); and a rationale, which is never graded. You turn this into a JSON Schema.

What a schema does not guarantee

An ai.agent step with a JSON schema returns output of that shape. The shape is all it guarantees. A proposal is worth what its evidence is worth, so check that each cited conversation exists and shows what the observation says.

Bounded tools

Give the evaluator ES|QL tools of your own that return aggregates or rows with a LIMIT. Open-ended exploration is slow: in Jeff Vestal's Self-Improving Agents workshop, bounded tools took about 4 tool calls in 30 seconds where the traces skill took about 32 calls in 8 minutes. What the traces carry. Each span in traces-agent_builder.otel-* has trace_id, name, @timestamp, duration and status.code, and under attributes: gen_ai.conversation.id, gen_ai.operation.name (invoke_agent, chat or execute_tool), gen_ai.tool.name, gen_ai.tool.call.arguments, gen_ai.tool.call.result, gen_ai.usage.input_tokens and gen_ai.usage.output_tokens. Your tools can read any of them.

The evaluator reads everything

It can read every trace, so it holds sensitive data. Give it only the privileges it reads with, and no tool that writes. Its own runs are traced into the same stream, so the week it reads includes its own conversations.

Propose, gate, apply, re-measure

Candidates are copies of the agent, its tools and its skills, so a gate never touches production. The gate runs the harness on the candidate and compares it with the comparison run: production's latest trusted measurement, m6-baseline before any apply, the last confirmed re-measure after one. Apply what passed, snapshot what it replaced, re-measure production, and roll back if the re-measure does not confirm the gain. Agent Builder keeps no version history of agents, so the ledger is the version history.

Variance and limits

The course design's "no regression" reads as no regression past a limit set outside the run-to-run spread. One run is a sample: a gain that vanishes on re-measure was noise.

What done looks like

  • Build 1: an evaluator with two or more bounded read-only tools, a schema that rejects malformed proposals, and runs that name the week's patterns with real evidence.
  • Build 2: gate.json equal to Cortex's policy, the passing proposal applied and confirmed, the trap not applied, and a ledger that replays to production.
  • Defend: the risk a gate would have caught, the row that stopped your trap, and what stops outside text.
