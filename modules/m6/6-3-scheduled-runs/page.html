Lab 6.3

Lab 6.3: Schedule recurring agent runs

The fraud desk starts work at three shift times in its own time zone. Cortex needs a canary that runs before each shift, a check after every deploy, and an audit of every answer that searched SARs.

Tip: Select Hide Instructions in the top bar to give the Brief full width.

The problem

A calendar schedule catches a change the next time it fires. It does not catch one the minute it lands. Cortex needs a check tied to the deploy, a check timed to the feed, and an audit tied to each answer: three needs, three patterns.

Three trigger patterns

Scheduled: an interval (every) or a calendar rule (rrule: freq DAILY, WEEKLY or MONTHLY, interval, byhour, byminute, byweekday, tzid). There is no cron syntax and the shortest interval is one minute. Ad hoc: a call to the workflow run API from whatever caused the need, such as a deploy script. Per-response: a post-execution workflow on the agent, run after every answer with the prompt, response and tool calls (each call carries its tool_id). It runs after every round, so to act on only some, test the tool calls inside the workflow: a foreach over inputs.tool_calls with an if whose condition reads foreach.item.tool_id : cortex.sar_search. Conditions use :, not ==.

Time zones

tzid defaults to UTC. Without byhour and byminute, a late run shifts every later run. Convert a stated time into one zone before comparing it with a window.

The canary

A small fixed question set, run unattended, recorded in the harness's schema so it compares with the baseline. Eight questions per run, each in a fresh conversation.

What a schedule costs

Tokens per run times runs per day, priced on M5's rate card. A schedule is a design input: an hourly canary costs eight times a three-times-daily one.

Who a schedule runs as

A scheduled workflow runs with the privileges of whoever last saved it. In production that last saver is a deliberate choice. Agent Builder access for service accounts exists; this lab does not teach it as a feature.

Reading the execution history

triggeredBy, status and step input and output separate three cases: did not run, ran and failed, ran and found nothing. Event triggers on Agent Builder conversations exist (Preview) and are named here, not used.

What done looks like

  • Build 1: a calendar rule with tzid matching the desk's shifts, no interval left, and one scheduled execution you watched.
  • Build 2: each need's pattern named, the deploy script calling the canary with the change id, a window trigger, and the audit attached after answers.
  • Defend: a pattern with reasons, your schedule's daily cost, and what an execution history shows.
